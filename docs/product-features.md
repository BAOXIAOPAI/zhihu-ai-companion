## 1. 产品定位与核心设计原则

**看山小盆** 是一台面向桌面的软硬一体智能陪伴植物设备，连接物理桌面看护与知乎社区内容生态。

本版功能规划确立三条核心原则：

1. **体验重心放在“陪伴感”**：通过 **Demo 级长期记忆 + 偏好管理 + 不定期主动提醒**，让小盆像一个记得你、懂你口味、会在恰当时机搭理你的桌面伙伴，而不只是“带屏幕的阈值报警器”。
2. **智能收口在软件侧，硬件做极简表现层**：所有记忆抽取、偏好调整、提醒调度、知乎检索与文案生成全部由后端完成；ESP32 固件只负责传感器采样、接收状态渲染动画与短句、播放 SD 卡预存音频以及触屏回执。
3. **Mock 优先，双模可切**：开发期与联调期通过网页模拟设备 + Mock 数据源跑通全闭环；接入真实知乎 API 后保留一键回退与异常自动降级到 Mock 的能力，保证开发效率与路演稳定性。

## 2. 硬件已有能力边界与动画映射

不新增任何硬件物料，全部功能严格建立在 [hardware-mechanical.md](hardware-mechanical.md) 已有硬件基础上：

- **显示与交互**：3.5 寸 480×320 电阻触摸横屏（仅展示文字、数值、卡片与位图/帧动画；无摄像头、无麦克风）。
- **环境感知**：空气温湿度（SHT31）、光照强度（VEML7700）、可拔插电容式土壤干湿状态（V1.2）；无水位计，靠 5 天水仓检查计时与人工确认。
- **音频输出**：DFPlayer Mini 播放 microSD 卡内预存固定 MP3（不支持硬件端动态语音合成）。
- **离线基线**：断网时可本地采样、触屏切屏、播放动画、触发 5 天提醒音、浏览最近一次缓存早报。

### 刘看山动态表情映射（复用官方赛事素材）

工作区已具备 6 组刘看山动态素材（**注：赛事授权仅限比赛期间用于参赛作品，赛后禁止商用**），直接映射为设备的 6 种展示姿态：

| 状态枚举 (`pose`) | 对应素材动作 | 适用场景 |
| --- | --- | --- |
| `idle` | 待机 | 植物屏日常默认状态 |
| `sway` | 晃悠 | 白天环境舒适、情绪轻松陪伴 |
| `greet` | 打招呼 | 刚配对成功、触发主动搭话/提醒 |
| `computer` | 电脑 | 切换到知乎早报屏、正在整理早报 |
| `sleepy` | 瞌睡 | 深夜低光照或进入勿扰时段 |
| `dribble` | 运球 | 刚完成水仓检查/补水、达成连续照顾里程碑 |

## 4. 对设备侧 v1 接口契约的补充锁定建议

为保证软件和硬件完全并行推进，建议在 [software-api.md](software-api.md) 基础上提前锁定以下设备通信细节（**H5 内部接口由软件侧独立迭代，不影响固件**）：

1. **配对与设备鉴权**
   - 约定设备首次开机或重置后如何展示/获取一次性配对码，绑定后设备持久化保存 `deviceToken` 到 NVS，后续请求携带统一鉴权头。
2. **`POST /api/device/telemetry` 字段与空值统一**
   - 固定字段：`sampledAt`（ISO 8601 UTC）、`temperatureC`、`humidityPct`、`lux`、`soilState`（`"normal" | "dry" | null`）、`soilDryMinutes`、`lastWaterCheckedAt`（ISO 8601 UTC 或 `null`，用于离线屏幕确认后的时间同步）。
   - 明确约定：拔掉土壤探头时 `soilState` 上报 `null`。
3. **`GET /api/device/sync` 增补轻量渲染字段**
   - 在已有 `settings`、`settingsVersion`、`pendingAction`、`briefVersion` 之外，增加：
     - `serverTime`：用于 ESP32 断网冷启动后校时；
     - `plantCaption`：植物屏当前展示的短句；
     - `companionNudge`（可为 `null`）：`{ nudgeId, text, pose, playTone, expiresAt }`，承载不定期提醒，硬件收到后直接渲染并按 `nudgeId` 回执。
4. **`POST /api/device/ack` 幂等确认**
   - 支持分别或批量确认 `settingsVersion`、`actionId`、`nudgeId`，确保网络抖动重试不重复触发提示音或重置 5 天计时。
5. **`GET /api/device/brief` 小屏文本硬约束**
   - 约定适合 480×320 字库与排版的最大长度（建议 `shortTitle` ≤ 18 汉字、`summary` ≤ 45 汉字），且后端严格清洗为纯 UTF-8 文本，剥离 HTML 标签和生僻 Emoji，防止花盆端乱码或截断溢出。

## 5. 知乎接口配额与模型使用约束（软件侧落盘要点）

结合团队已实测的 [知乎接口实测速查](../../知乎接口实测速查.md) 与 [赛事指南](../../技术支持/zhihu/references/hackathon.md)：

- **额度分配**：`zhihu_search`（5000 次/天）作为早报召回主力；`hot_list`（100 次/天）和 `zhida_openai`（100 次/天）必须做后端缓存与去重，禁止随每次轮询或刷新直接穿透。
- **直答模型选择**：若使用知乎直答接口，选用 `zhida-fast-1p5`（实测 ~1.9s），避免 `zhida-agent`（实测近 57s 且易超时）。同时赛事不限制底层大模型，复杂记忆抽取与多风格生成可结合通用大模型完成。
- **链接校验**：早报卡片 `url` 严禁由大模型自由生成，必须直接使用检索接口返回的真实知乎链接。

## 6. 建议提交给硬件队友确认的 4 个小问题

在正式锁定接口文档前，可和队友快速核对这 4 项即可：

1. **屏幕文字长度上限**：480×320 布局里，刘看山动画区和文字区分别占多大，`plantCaption`、`shortTitle`、`summary` 各自最多能放多少个汉字？
2. **字库与字符集**：固件端是内置固定常用汉字库还是挂载全量点阵/TTF 字库（决定是否需要严格过滤生僻字和标点）？
3. **音频文件清单**：除 `/mp3/0001.mp3`（5 天提醒）和 `/mp3/0002.mp3`（操作确认音）外，是否方便多预存 1 个 `/mp3/0003.mp3` 作为“不定期搭话轻提示音”（若不便，也可完全仅靠屏幕气泡+动图表现）？
4. **设备配对方式**：首版原型是先由后端预置测试设备账号直接联调，还是设备端开机请求接口拿 6 位配对码显示在屏幕上？
